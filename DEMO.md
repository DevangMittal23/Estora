# Demonstration walkthrough

Start `npm run demo` and open http://localhost:5173. All figures are dummy academic data.

1. Browse the landing page and marketplace. Filter by city/type, search and adjust price/funding ranges. Open a property, switch gallery images and try the projected return calculator.
2. Sign in as `investor1@estora.dev / Investor@123`. Review active and exited holdings, realised ROI, allocation chart and transaction history. Make a labelled mock top-up. Buy one unit in a LIVE property, review the confirmation and inspect the new investment/ledger debit.
3. Sign out and sign in as `broker1@estora.dev / Broker@123`. Inspect listing funding timelines, investor units and commission. Create a property through the five-step wizard; save and reload to demonstrate draft restoration. Upload three dummy images and a document, then submit.
4. Sign in as `admin@estora.dev / Admin@123`. Approve the submitted listing. Show broker/user approval and pending KYC document review. Change fee/ownership settings. Move the FUNDED seed property to HOLDING or open the existing HOLDING property.
5. Preview a sale on the HOLDING property. Verify that investor payouts equal distributable proceeds; confirm execution. Sign in as an investor to see the credit and exited holding. Try repeating the sale through the API: `ALREADY_SOLD` prevents a second payout.
6. As admin, cancel a LIVE property with investors. Show complete REFUND entries and zero sold units. Review a withdrawal request, then approve/reject it and inspect the corresponding notification.
7. Send a property enquiry as investor and reply as its broker. Show unread notification counts and mark-as-read.

For a concise 3–5 minute recording, prioritize steps 1–5 and briefly show cancellation, KYC and settings. A recording has not been generated by this implementation.

## Concurrency proof

Run `npm --prefix server test`. The `CP2: simultaneous requests for last units cannot oversell` test runs 100 generated real-database scenarios. It submits two requests for the remaining units concurrently and asserts exactly one success, one `INSUFFICIENT_UNITS`, one commission and an exact sold-unit count. `CP4` separately checks simultaneous requests sharing an idempotency key.

For a two-window manual demonstration, use separate browser profiles so each investor has a separate localStorage session. Prepare a LIVE property with enough remaining units that each investor can purchase the final quantity within the configured ownership cap. Confirm both checkouts simultaneously; one succeeds and the other receives the remaining-units error. Normal tabs in the same browser share authentication storage.
